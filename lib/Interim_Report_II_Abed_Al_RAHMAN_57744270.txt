Abstract
The logistics industry in Hong Kong faces persistent operational challenges stemming from
fragmented digital tools, overall inefficient route planning, and a lack of unified platforms that
serve both administrative coordinators as well as field-based delivery personnel. Moreover,
despite Hong Kong’s position as a leading logistics hub in the Asia-Pacific region, small to
medium-sized logistics enterprises often lack access to integrated technological solutions that
larger corporations employ, resulting in suboptimal delivery routes, communication breakdowns
between dispatchers and drivers, and inefficient proof-of-delivery mechanisms.
This project presents OrderVista, an AI-enhanced delivery management platform (software) designed specifically for the Hong Kong logistics context. OrderVista provides a unified
solution that bridges the gap between back-office administration and frontline delivery operations
through a dual-interface architecture: a web-based administrative portal for dispatchers and
managers, and a mobile application for delivery drivers. The platform integrates multiple
technological components including route sequencing, real-time task management, AI-powered
natural language assistance, and a comprehensive proof-of-delivery system.

System Architecture and Design
The OrderVista platform is built using Flutter for cross-platform application development,
enabling deployment across web, Android, and iOS from a single codebase. The backend
infrastructure leverages Supabase, providing PostgreSQL database services, authentication,
real-time subscriptions, and secure file storage. External service integrations include Mapbox for
geocoding and map visualization, and the DeepSeek large language model API for AI-powered
features. The system implements a multi-tenant architecture using Row-Level Security (RLS)
policies, ensuring complete data isolation between different logistics companies sharing the
platform.

Current Implementation Achievements
The administrative portal enables dispatchers to create and manage delivery tasks through both
manual entry and CSV bulk import with validation. A baseline route sequencing algorithm,
implementing a nearest-next heuristic approach, orders tasks to reduce travel distance. The
system generates visual route previews using Mapbox static map APIs, allowing dispatchers to
verify routes before assignment. On the mobile app for drivers or dispatchers, an AI assistant
integration provides two key capabilities: automated summary generation that synthesizes task
batches into natural language briefings, and a conversational chat interface that allows them to
query task information using everyday language.
Furthermore, the driver application provides field personnel with a streamlined interface
for viewing assigned tasks, capturing proof of delivery through photographs and notes, and
maintaining synchronization with the central system. Importantly, the workflow is designed to
require proof of delivery before a task can be marked as completed. This control is implemented
in the prototype and has been validated in emulator and web testing, while final end-to-end
validation on a physical device remains pending. The implemented authentication system
supports role-based access control, distinguishing between administrative and driver roles while
maintaining tenant isolation across different logistics companies.

Preliminary Results
Functional testing confirms that core features of the system operate as designed. Performance
measurements conducted in City University of Hong Kong’s network environment indicate
that typical operations complete within acceptable latency thresholds: task creation averages
3 seconds, route generation completes in approximately 2.1 seconds, and AI summary generation returns results within 3.2 seconds. The geocoding API responds in an average of 127
milliseconds per address lookup. Security validation confirms that the Row-Level Security
implementation successfully enforces tenant isolation; i.e., users cannot access data belonging to
other organizations.

Planned Enhancements for Next Iteration
While the current prototype demonstrates substantial core functionality, the next phase of development will introduce advanced features to enhance various aspects of operational intelligence
and automation. These enhancements include:
Driver Management and Optimization: The system will be extended to display available
drivers to administrators, with drivers able to indicate their availability status from the mobile
application. A recommendation engine will suggest optimal driver assignments based on drivers’
current locations and proximity to delivery clusters, moving beyond simple path optimization
to holistic resource allocation. The optimization objective will focus on minimizing overall
driving distance across the fleet, recognizing the fact that fewer optimally-positioned drivers
may outperform a larger number of poorly-distributed ones.
Customer Communication and Tracking: A package tracking feature will enable customers
to inquire about delivery status using tracking IDs or references. Administrators will be able to
provide real-time progress updates based on driver locations and task completion status.
Agentic AI Capabilities: The AI assistant will evolve from a query-response tool to
an agentic system capable of automating driver actions. This includes automatically sending
customer notifications such as “Your delivery is almost there” or “Please be at this location,”
reducing manual communication overhead for drivers while keeping customers informed.
Real-Time Communication: A live chat feature will enable direct communication between
administrators and drivers, facilitating rapid problem resolution and coordination during active
delivery operations.
Automatic Task Sorting: The driver task list will automatically reorder after each task is
marked as completed, ensuring drivers always see their next priority task at the top.
Beyond feature enhancements, the final phase will address production readiness: security
tightening through enhanced cryptographic measures, Android application packaging, Google
Play Store publishing, real-world user testing with actual logistics personnel, and resolution of
any outstanding issues identified during field trials.

Significance and Contribution
OrderVista addresses a genuine market need for accessible, intelligent logistics management
tools tailored to the Hong Kong context. The current prototype demonstrates the technical
feasibility of the platform architecture and core workflows, establishing a solid foundation upon
which advanced optimization and automation features will be built.
The creative aspects of this project include: (1) the integration of conversational AI for
logistics task queries, with a roadmap toward agentic automation capabilities; (2) the unified
codebase approach using Flutter that delivers consistent experiences across web and mobile
platforms; (3) the multi-tenant architecture with Row-Level Security providing enterprisegrade data isolation; and (4) the planned driver-cluster optimization approach that prioritizes
minimizing total fleet distance rather than simply assigning tasks to the nearest available driver.
In summary, this Interim Report II presents a designed and substantially implemented
delivery management platform that integrates modern web technologies, cloud services, and
artificial intelligence to address real-world logistics challenges in the Hong Kong market. The
current prototype validates the core architecture and demonstrates essential workflows, while
the planned enhancements for the next iteration will introduce the advanced optimization and
automation features that will differentiate OrderVista as a comprehensive logistics solution. The
preliminary results indicate that the foundation is solid and performant, positioning the project
well for the ambitious final phase of mobile and web development.

Introduction

Problem Context

The logistics and delivery industry in Hong Kong operates within a uniquely demanding
environment. As one of the world’s most densely urbanised cities and a major logistics hub

6

in the Asia–Pacific region, delivery operations must contend with congested road networks,
time-sensitive service expectations, and the continual coordination of multiple vehicles across
compact geographic areas (Chan, 2025; Hong Kong Productivity Council, 2025). These pressures
are particularly acute for small and medium-sized logistics enterprises, which may lack access to
the sophisticated fleet-management systems adopted by larger corporations.
Operational challenges for logistics coordinators are also multifaceted. Dispatchers often
do not have a single unified platform to assign daily tasks, monitor progress, and communicate
with drivers in real time. Drivers, in turn, frequently rely on fragmented tools: tasks may arrive
through one channel, navigation occurs in another, and proof-of-delivery (PoD) reporting is
handled separately. This fragmentation can lead to suboptimal routing decisions, communication
delays, and inefficient PoD processes, ultimately increasing operating costs and reducing customer
satisfaction.
Beyond commercial implications, poorly coordinated logistics operations can affect
worker welfare. Drivers navigating unfamiliar locations under time pressure, without adequate
route guidance or communication tools, may experience elevated stress and associated safety
risks (Apdullah et al., 2021). A comprehensive digital solution that improves both operational
efficiency and the driver experience therefore represents a meaningful contribution to the industry.

2.2

Proposed Solution

OrderVista is a delivery management platform designed to address these challenges through
a unified, AI-enhanced approach. The system provides two complementary interfaces: (i) a
web-based administrative portal for dispatchers and managers, and (ii) a mobile application for
delivery drivers. This dual-interface architecture ensures that each stakeholder in the delivery
workflow has access to appropriate tools and information.
The administrative portal supports creation and management of delivery tasks, bulk
import of task batches from CSV files, generation of route sequences, and review of PoD
submissions. The driver application provides assigned task lists, navigation support through
integrated mapping, and PoD capture using photographs and notes.
A distinguishing feature of OrderVista is the integration of a large language model (LLM)

7

as an AI assistant. The assistant enables drivers to interact with the system using natural-language
queries (e.g., task summaries and operational questions), reducing the learning curve for less
technically oriented users and accelerating access to relevant information without navigating
complex menus.

10

emerging application of artificial intelligence in logistics operations. The section concludes by

3.1

Path Optimization Algorithms

At the heart of logistics optimization lies the Vehicle Routing Problem (VRP), a combinatorial
optimization challenge that has engaged researchers for over six decades (Dantzig & Ramser,
1959). The VRP seeks to determine optimal routes for a fleet of vehicles serving geographically
distributed customers, with the objective of minimizing total travel distance, time, or cost while
satisfying operational constraints. The problem is classified as NP-hard, meaning computational
complexity increases exponentially with problem size, making exact solutions impractical for
real-world scenarios with numerous delivery points (Laporte, 2009).
Foundational Algorithms
Classical shortest-path algorithms form the building blocks for routing solutions. Dijkstra’s
algorithm computes optimal paths in weighted graphs by progressively expanding from a source
node, guaranteeing the shortest path when all edge weights are non-negative (Dijkstra, 1959).
While foundational, Dijkstra’s algorithm addresses point-to-point navigation rather than the
multi-stop sequencing required in delivery operations.
The A* algorithm extends Dijkstra’s approach by incorporating a heuristic estimate of
remaining distance to the destination, directing the search toward promising regions and reducing
computational overhead (Hart et al., 1968). A* excels in point-to-point pathfinding applications,
from interactive navigation to real-world routing, but typically serves as a component within
broader VRP frameworks rather than a complete solution (Irnich & Desaulniers, 2005).
Metaheuristic Approaches
Given the computational intractability of exact VRP solutions at scale, metaheuristic approaches
have become essential for practical applications. These methods sacrifice guaranteed optimality
for the ability to find high-quality solutions within acceptable time constraints. Two widely
studied families are:

11
1. Ant Colony Optimization (ACO). ACO draws inspiration from the foraging behavior of
ants, where artificial agents construct solutions while depositing virtual pheromones that
influence subsequent iterations. Stronger pheromone trails on shorter paths create positive
feedback, progressively improving solution quality (Dorigo & Gambardella, 1997). ACO
has demonstrated effectiveness across VRP variants including capacity-constrained and
time-windowed problems.
2. Genetic Algorithms (GAs). GAs simulate natural selection by maintaining a population of
candidate solutions (routes) that evolve through selection, crossover, and mutation operators.
Over successive generations, the population converges toward increasingly fit solutions.
GAs have proven versatile across complex VRP variants, including environmentallyfocused formulations such as the Green VRP that minimizes emissions rather than distance
alone (Erdoğan & Miller-Hooks, 2012).
For the OrderVista prototype, a nearest-next heuristic provides the baseline sequencing
algorithm, i.e., a greedy approach that iteratively selects the closest unvisited destination. While
not optimal, this approach offers computational simplicity suitable for an initial implementation,
with the architecture designed to accommodate more sophisticated algorithms in future iterations.

3.2

Traffic Congestion and Real-Time Adaptation

Effective route planning must accommodate the dynamic nature of urban traffic networks. A
route that appears optimal during planning may become suboptimal as congestion develops.
Real-time traffic awareness has therefore become essential for practical routing applications (Jain
et al., 2023).
Floating Car Data (FCD)
Floating Car Data (FCD) systems collect anonymized, timestamped GPS data from vehicles
equipped with navigation applications or cellular connectivity. This crowdsourced approach
provides dense coverage of traffic conditions without dedicated sensor infrastructure. FCD
enables real-time speed estimates across road segments, supporting dynamic route adjustments

12

as conditions change (Herrera et al., 2010).
Modern navigation applications such as Google Maps and Waze leverage FCD from
large user populations to provide traffic-aware routing. The effectiveness of these systems scales
with user adoption, creating network effects that benefit all participants.
Predictive Traffic Models
Beyond real-time monitoring, predictive models attempt to forecast traffic conditions based on
historical patterns, time-of-day factors, and special events. Machine learning approaches have
shown promise in capturing complex traffic dynamics, enabling proactive route planning that
anticipates congestion before it materializes.
For logistics applications, combining historical patterns with real-time FCD can offer
a robust approach: using predictions for advance planning while retaining the ability to adapt
when actual conditions diverge from expectations.

3.3

Offline Navigation Technologies

Reliable navigation in logistics operations must account for connectivity limitations. Drivers
traversing areas with poor cellular coverage, underground parking facilities, or dense urban
canyons may lose access to cloud-based navigation services precisely when guidance is most
needed.
Offline navigation solutions address this challenge by caching map data, routing algorithms, and relevant waypoints on the device. Technologies such as OpenStreetMap provide
freely available geographic data suitable for local storage, while efficient routing algorithms
optimized for mobile processors enable on-device pathfinding without network dependency.
For OrderVista, offline capability is particularly relevant for the driver application. While
the current prototype assumes connectivity for synchronization, the architecture accommodates
future offline enhancements through local task caching and deferred synchronization mechanisms.

3.4

Proof of Delivery and Last-Mile Digitization

The final stage of the logistics chain, i.e., last-mile delivery, represents a critical juncture where
operational efficiency, customer satisfaction, and accountability converge. Despite its strategic
importance, the last-mile segment has historically suffered from fragmented documentation
processes and limited real-time visibility (Bhattacharjee et al., 2024). Proof of Delivery
(PoD) serves as the definitive confirmation that goods have reached their intended recipients in
acceptable condition, establishing a chain of custody essential for dispute resolution and revenue
recognition (Nguyen, 2024).
Traditional paper-based PoD systems can introduce significant operational inefficiencies.
Manual signature collection, physical document handling, and delayed confirmation create gaps
in accountability, complicate invoice reconciliation, and limit real-time visibility into delivery
status (Bhattacharjee et al., 2024). The transition to digital PoD mechanisms addresses these
limitations through mobile capture of signatures, photographs, GPS timestamps, and delivery
notes at the point of service. Prior work reports that digital PoD systems can reduce manual
errors, accelerate administrative workflows, and provide stronger documentation for dispute
resolution (Nguyen, 2024).
Integrating real-time PoD capabilities with Transportation Management Systems (TMS)
enables broader operational visibility. By providing near-immediate confirmation upon delivery
completion, logistics coordinators can monitor fleet performance, identify bottlenecks, and
communicate more accurate delivery windows to customers (Bhattacharjee et al., 2024). For
OrderVista, enforcing PoD capture before task completion represents an architectural commitment
to accountability aligned with last-mile digitization practices.

3.5

Multi-Tenant Security and Data Isolation

Multi-tenancy has emerged as a foundational architectural pattern for Software as a Service
(SaaS) platforms, enabling multiple organizations to share infrastructure while maintaining
logical data separation. The security implications of multi-tenant architectures are significant: a
single breach in isolation mechanisms can expose sensitive data across organizational boundaries,

14

resulting in severe trust violations and compliance risks (Abdul et al., 2018). Prior work identifies
three primary approaches to tenant isolation: separate databases per tenant, separate schemas
within shared databases, and shared schemas with application-level or database-level access
controls (Abdul et al., 2018; Gao et al., 2011).
The separate database approach provides strong isolation by allocating dedicated database
instances to each tenant, physically segregating data stores and reducing cross-tenant attack
vectors (Abdul et al., 2018). However, this model incurs operational costs, management
complexity, and scalability limitations as tenant populations grow. Conversely, shared schema
architectures consolidate tenant data within common tables, maximizing resource efficiency and
supporting larger tenant populations, but increasing the burden on access control correctness
(Gao et al., 2011).
Row-Level Security (RLS) represents a database-enforced isolation mechanism that
centralizes access control at the data layer rather than relying solely on application logic. By
defining security policies directly on database tables, RLS helps ensure that queries are filtered
based on authenticated user context, reducing the risk of inadvertent cross-tenant data access even
in the presence of application-level errors (Amazon Web Services, 2020). Research also suggests
that well-designed multi-tenant service models can reduce operational and storage overhead
compared to full isolation approaches, while still meeting practical security requirements when
combined with role-based access control (Hattab et al., 2023). For OrderVista’s multi-tenant
architecture, RLS policies across operational tables provide the isolation mechanism required to
support multiple logistics companies from a shared infrastructure.

3.6

Artificial Intelligence in Logistics

The emergence of sophisticated AI systems, particularly large language models (LLMs), presents
new opportunities for logistics applications. This section examines the evolution of conversational
AI, its potential application in operational contexts, and key reliability considerations.

15

Evolution of Conversational AI
Conversational interfaces have progressed from rule-based chatbots with limited vocabulary to
neural language models capable of understanding and generating natural language across diverse
domains. Early systems required extensive manual scripting of responses; modern LLMs learn
language patterns from large text corpora, enabling flexible interaction without domain-specific
programming (Brown et al., 2020).
Large Language Models for Decision Support
State-of-the-art LLMs (e.g., GPT-style models, Claude, and DeepSeek) demonstrate strong
capability in contextual understanding, information synthesis, and coherent response generation.
In enterprise contexts, these models can act as intelligent assistants that help users navigate
complex information without requiring technical expertise (Brynjolfsson et al., 2023).
Key capabilities relevant to logistics applications include:
• Information synthesis: Summarizing large volumes of operational data into digestible
briefings.
• Natural language queries: Allowing users to ask questions in everyday language rather
than constructing formal database queries.
• Contextual understanding: Interpreting questions within operational context (e.g.,
understanding that “today’s deliveries” refers to the current date and the authenticated
user’s assignments).
LLM Reliability and Operational Risks
While LLMs demonstrate strong capabilities in natural language understanding and generation,
their deployment in operational contexts introduces reliability concerns. The phenomenon
of hallucination, where LLMs generate plausible but factually incorrect outputs, represents
a meaningful risk in enterprise applications (Ji et al., 2024). Prior work on LLM errors and
hallucinations highlights that factual accuracy can vary across tasks and domains, and that

16

temporal and factual reliability may be challenging without appropriate grounding and controls
(Lavrinovics et al., 2025; Twist et al., 2025).
The operational implications of hallucinations extend beyond technical considerations
into safety, compliance, and reputation. In logistics contexts, incorrect AI outputs could direct
drivers to incorrect addresses, generate inaccurate delivery summaries, or provide customers
with misleading status updates, all of which can degrade service quality and customer trust (Ji
et al., 2024).
Mitigation strategies emphasize multi-layered approaches combining technical controls
and human oversight. Cross-checking and validation mechanisms (e.g., verifying AI outputs
against trusted system data) can help detect inconsistencies (Lavrinovics et al., 2025). Confidence
thresholding and restricting actions to high-certainty outputs can reduce error propagation while
maintaining utility for well-scoped queries. Evidence on productivity gains from deployed
generative AI systems suggests operational value when systems are designed with appropriate
guardrails and oversight (Brynjolfsson et al., 2023). In OrderVista, LLM outputs are treated as
decision-support content and are complemented by workflow controls and human verification
(e.g., dispatcher review and driver confirmation) to reduce the operational impact of incorrect
responses.
Application in Logistics Operations
At present, conversational AI specifically embedded within last-mile logistics operations remains
relatively underexplored compared to general-purpose enterprise use. Existing logistics software
typically relies on structured interfaces (forms, tables, dashboards), requiring users to understand
the system’s information architecture. For frontline workers such as delivery drivers, who may
have limited time or technical background, natural language interaction offers a lower barrier to
information access.
Potential applications include:
• Drivers querying “What’s my next delivery?” rather than navigating task list interfaces.
• Dispatchers asking “Which driver has the lightest load today?” to inform assignment
decisions.

17
• Automated generation of shift summaries highlighting completed tasks, exceptions, and
pending items.
Recent developments indicate growing interest in AI-augmented logistics tools, including
exploratory work on LLM opportunities and challenges in supply chain management (Addepto,
2024; Krishnamoorthy et al., 2024; Zahid & Lazaravičius, 2026). However, comprehensive
platforms that integrate LLMs tightly with operational workflows (task management, routing,
PoD, and secure multi-tenant data access) remain limited.

3.7

Similar Delivery Systems and Comparative Positioning

This subsection reviews representative delivery and dispatch systems to extract common product
properties and position OrderVista relative to established platforms. The goal is not to reverse
engineer proprietary implementations, but to identify system-level capabilities (e.g., dispatch
model, routing support, worker experience) that shape last-mile performance and user adoption.
System categories and operating models
Comparable systems can be grouped into three broad categories.
(1) On-demand, two-sided gig platforms (e.g., Uber Eats and foodpanda). These platforms
coordinate matching among consumers, merchants, and couriers through centralized
dispatch algorithms and standardized mobile workflows. Their primary objectives
emphasize marketplace liquidity, service-level targets, and balancing supply and demand
at scale rather than tailoring operational controls to an individual logistics enterprise
(Cachon et al., 2017; Einav et al., 2016). In this model, the platform typically defines the
core workflow constraints (e.g., acceptance flows, standardized status transitions), and
operational customization is constrained by platform-wide policies.
(2) Enterprise and SME delivery management and dispatch systems. Traditional dispatch
systems (often described under fleet management, delivery management systems, or
transportation management systems) focus on supporting a company’s internal operations:
creating delivery jobs, assigning drivers, monitoring progress, and capturing delivery

18

outcomes (Bhattacharjee et al., 2024; Laporte, 2009). These products frequently provide
configurable operational controls (roles, operating rules, reporting), but may impose
adoption barriers for smaller firms due to setup cost, training overhead, and feature
complexity (Bhattacharjee et al., 2024).
(3) Navigation-first systems (e.g., Google Maps and Waze as components). Navigation
applications excel at point-to-point routing and real-time traffic awareness but do not, by
themselves, provide dispatch primitives such as job creation, driver assignment, proof-ofdelivery records, or operational communication (Herrera et al., 2010; Jain et al., 2023). In
delivery operations, navigation is therefore a component inside a wider dispatch workflow.
Extracted properties for comparison
From these categories, the literature and common industry practice suggest a set of properties
that materially affect last-mile delivery performance and user experience: (i) operational fit to the
local context (addresses, building access patterns, dense urban routing), (ii) dispatch workflow
cohesion (task creation, assignment, execution, and completion), (iii) optimization objectives
(distance/time/cost, time windows, multi-driver), (iv) worker-facing usability and cognitive load,
and (v) the ability to incorporate new capabilities rapidly as requirements evolve.
Large language models introduce an additional dimension: interaction elasticity, i.e.,
whether a frontline user can obtain operational answers or summaries via natural language rather
than navigating structured dashboards. LLM-based assistants have been shown to improve access
to information and productivity in knowledge work settings, but require careful grounding and
guardrails due to hallucination risk (Brynjolfsson et al., 2023; Ji et al., 2024). Recent work
further highlights the importance of constraining tool use and verifying outputs when LLMs
are given more autonomy (often referred to as agentic or tool-using systems) (Ji et al., 2024;
Lavrinovics et al., 2025). In this report, agentic AI refers to tool-using LLM-based systems that
can invoke actions (e.g., calling APIs or triggering workflow steps) rather than only generating
text, and therefore require explicit constraints and oversight (Ji et al., 2024; Lavrinovics et al.,
2025).

The literature indicates that routing optimization, traffic awareness, last-mile digitization,
and conversational AI are well-studied themes, but comparable systems often combine these
capabilities in ways that do not fully serve the specific needs of Hong Kong SMEs. The
comparative analysis in Section 3.7 highlights a set of gaps that motivate OrderVista:
1. Fragmented tooling in day-to-day delivery work. Logistics workers often rely on
multiple disconnected applications for different aspects of their workflow (task management,
navigation, communication, proof of delivery), particularly in small to medium-sized
companies.
2. Adoption barriers for SMEs. Sophisticated optimization and analytics capabilities
remain concentrated in enterprise solutions that can be difficult for smaller operators to
adopt due to setup and training overhead.
3. Operational fit to Hong Kong SMEs. Many international systems optimize for broad
applicability or marketplace-scale objectives, while Hong Kong SME dispatch workflows
require a tighter fit to dense urban constraints and local operating practices (Hong Kong
Productivity Council, 2025).
4. AI as workflow assistance rather than a separate interface. Although LLMs can
synthesize and answer questions effectively, logistics tools often rely on structured
dashboards that increase cognitive load for frontline workers. AI-native interaction
remains underutilized in day-to-day dispatch execution (Brynjolfsson et al., 2023; Ji et al.,
2024).
5. Reliability requirements for operational AI. Hallucination and other failure modes can
be costly in logistics contexts, motivating grounding, verification, and guardrails (Ji et al.,
2024; Lavrinovics et al., 2025).

22
6. Roadmap to safe agentic assistance. Moving from reactive Q&A to agentic (toolusing) automation can reduce manual communication and task coordination, but requires
safeguards to mitigate hallucination and unintended actions (Ji et al., 2024; Lavrinovics
et al., 2025).
7. Iteration speed aligned to operator needs. Marketplace platforms must govern changes
across large ecosystems, which can constrain rapid, operator-specific feature delivery. A
dedicated operator tool can prioritize faster experimentation and refinement for the target
users (Einav et al., 2016; Parker et al., 2016).
OrderVista addresses these gaps by providing a unified dispatch platform that integrates
task management, route sequencing, proof of delivery, and AI-powered assistance within a single
system accessible to both administrators and drivers. The multi-tenant architecture enables
small and medium logistics enterprises to access capabilities previously available only to large
organizations, while explicitly prioritizing the Hong Kong context and establishing a path toward
agentic capabilities under guardrails and human oversight.

Data Model

The database schema implements a multi-tenant architecture in which operational tables include
a company id foreign key, enabling RLS policies to enforce tenant isolation at the database
layer (Amazon Web Services, 2020). The schema has been deployed on Supabase PostgreSQL.
Core Entities
Companies and members: The companies table serves as the tenant registry, storing
organization details. The company members table associates authenticated users with companies,
storing role assignments (admin or driver) and profile information. This structure supports
multiple users per company and enables role-based access control.

25
Tasks: The tasks table represents individual delivery assignments, storing recipient
information, delivery address, scheduling data, status tracking, and assignment to specific drivers.
Tasks belong to a company and optionally reference an assigned driver (company member).
Routes and route tasks: The routes table stores generated route containers with metadata including optimization method, distance estimates, and assigned driver. The route tasks
junction table links tasks to routes with sequence numbers, enabling ordered traversal of delivery
stops.
Telemetry, Synchronization, and Media
Telemetry events: The telemetry events table captures location updates, status changes, and
operational events from the driver application. Events include timestamp, event type, coordinates,
and associated task references (where applicable).
Media: The media table stores references to files uploaded to Supabase Storage,
primarily proof-of-delivery photographs. Records include file paths, MIME types, upload
timestamps, and associations to tasks and uploading users.
Safety Rules and Communication
Safety rules: The safety rules table enables companies to define operational constraints
such as maximum driving hours, restricted delivery windows, or geographic boundaries. Rules
are configurable per company.
Messages (planned): The schema includes provisions for a messages table to support
future real-time communication between administrators and drivers. This feature is planned for
the next development iteration.

6.3

Routing Optimisation Evaluation (Distance and Time Proxy)

This subsection evaluates the quality of route sequencing produced by the implemented nearestnext heuristic (Section 5.4). This is distinct from system latency (Section 6.2), which measures
how long operations take from the user perspective. Here, the focus is whether the algorithm
reduces distance and a distance-based time proxy. In this report, cost is treated qualitatively as
proportional to distance (fuel) and time (labor), so relative improvements mirror the distance
and time proxy.

58

Evaluation setup
To assess optimisation quality, the same set of delivery stops was sequenced using multiple
methods and compared using consistent metrics.
Compared methods.
1. Unoptimised order (baseline): tasks executed in their original input order (e.g., CSV
order or creation order).
2. Nearest-next heuristic (OrderVista): greedy selection of the next closest unvisited stop
based on geographic distance (Algorithm 5.1).
Metrics. Two primary metrics are reported:
• Total route distance (km): computed from consecutive stop pairs using the Haversine
great-circle distance (Equation 1).
• Estimated travel time (min): reported as a distance-proportional proxy to support relative
comparison across methods (i.e., shorter distance implies lower expected time in typical urban
driving conditions).
Test data. Measurements were performed on Hong Kong delivery addresses representative of dense urban delivery patterns (e.g., mixed commercial/residential stops across Hong
Kong Island and Kowloon). Stop counts were evaluated at multiple batch sizes consistent with
typical dispatcher route creation in the prototype.
Results
Table 16 summarizes the observed improvements in distance and time. The nearest-next
heuristic consistently reduces total route distance relative to the unoptimised baseline, indicating
that OrderVista performs meaningful route optimisation rather than merely reordering stops
arbitrarily.

Interpretation: The observed reductions align with the intended behavior of nearest-next
sequencing: by selecting geographically closer consecutive stops, the algorithm reduces avoidable

Limitations of the evaluation. Two limitations should be noted. First, Haversine distance does

These limitations motivate future evaluation using road-network routing and scenario-based
traffic benchmarks, but do not change the conclusion that the current system provides meaningful
optimisation relative to an unoptimised baseline.

• Smart communication: Draft messages for driver approval before sending to customers.

1.1

Monthly Project Logs

October 2025

During the period from September to October 2025, work on the OrderVista unified logistics
platform commenced with an intensive phase of research and foundational prototyping. The initial
weeks were dedicated to reviewing best practices in logistics technology and relevant literature on
vehicle routing algorithms, traffic data integration, and emerging AI/LLM applications in supply
chain management. In parallel, market and competitor analysis was conducted to evaluate the
strengths and limitations of existing logistics solutions, with particular attention to requirements
relevant to the Hong Kong operational context.
On the technical side, a new project was initialized using Flutter to provide a crossplatform foundation for both mobile and web applications. The development workspace and
source control were configured, and a blank scaffold was created to serve as the backbone for
subsequent interface and feature development. Progress continued through incremental design
and integration of core UI elements, including navigation menus, template screens, and baseline
layout structures.
By the end of October, a clear technical roadmap had been established, with key
documentation and design notes consolidated and an initial application structure in place. This
research and early development phase provided the foundation for implementing core system
functions and refining user experience in the subsequent stages.

1.2

November 2025

In November 2025, the development of OrderVista entered its third month, with progress focused
on translating plans into working components and improving the overall application structure as
a solo developer. Building on the initial research and scaffold established earlier, the work this
month emphasized iterative prototyping and strengthening core engineering practices.
Key activities included refining the user interface by implementing consistent theming
and layout conventions to promote a unified look and feel across devices. Effort was also invested

72

in setting up reusable UI components and navigation patterns to support efficient development in
later stages. Initial experimentation began with integrating essential Flutter packages for state
management and navigation.
In addition, November included drafting early data models tailored to logistics operations
and establishing scalable directory and file organization. Mock screens for order tracking,
delivery routing, and task overview were implemented to better visualize the intended workflow.
Documentation was also started to capture key design decisions and planned extensions.
Throughout the month, regular self-testing and small iterations were used to maintain
steady progress and reduce integration risk. The groundwork established in November positioned
the project for integration of back-end logic, user interactions, and advanced features in the
subsequent development cycle.

1.3

December 2025

During December 2025, the OrderVista effort shifted from UI scaffolding to engineering a more
production-ready foundation. Environment management was formalized through .env workflows,
a centralized AppConfig, and a bootstrap layer to orchestrate initialization, dependency injection,
and future testing seams.
The driver client adopted a repository architecture supported by a Drift-powered offline
cache, enabling cached task persistence, demo seeding, and an observable synchronization state
within the UI. In parallel, a full Supabase schema was authored and documented, including
multi-tenant tables, functions, RLS policies, and seed data, along with backend contracts and an
updated milestone plan.
Collectively, these artifacts aligned the codebase with the interim report architecture
and established the groundwork for subsequent integrations, including Supabase authentication,
background synchronization queues, telemetry ingestion, and the dispatcher portal.

1.4

January 2026

During January 2026, the OrderVista project integrated Supabase into the Flutter application,
replacing mock REST calls with live queries against the deployed multi-tenant schema. The

73

service layer now fetches driver tasks filtered by company and driver ID while respecting RLS
policies for tenant isolation.
The Drift cache layer stores tasks locally, presenting cached data immediately on startup
while synchronizing with remote updates asynchronously. The .env file was populated with
Supabase credentials, Mapbox tokens, and an API key for AI integration. The AppConfig
singleton exposes these values as typed accessors throughout the codebase.
The task list UI was enhanced to display connectivity state and cache indicators, showing
whether data is live, cached, or demo-seeded, including last synchronization timestamps. At
the end of January, the driver client successfully reads real tasks from Supabase and caches
them locally. Offline mutation queues, driver authentication hardening, telemetry streaming, and
deeper Mapbox integration remain planned work for the next phase.

1.5

February 2026

The scope of the OrderVista project expanded considerably this period as both the driver mobile
application and the administrative portal reached functional maturity. On the driver side, the
task list screen now supports full proof of delivery workflows including barcode and QR code
scanning via the device camera, photo capture for delivery evidence, and real time upload of
proof artifacts to Supabase Storage. A telemetry panel was introduced allowing drivers to
manually send location pings or toggle continuous background updates, with status indicators
and geofence proximity alerts displayed alongside tasks. The integration of DeepSeek as the AI
backend enables one tap summaries and conversational chat about the day’s workload directly
within the task interface.
The administrative portal evolved from a basic scaffold into a comprehensive fleet
management tool. Administrators can now create individual delivery tasks with geocoded
addresses, assign drivers by email or UUID, and schedule start times. A bulk CSV import
feature was implemented supporting flexible column mappings, automatic address geocoding via
Mapbox, and chunked database inserts for large files. The route sequencer generates optimized
delivery sequences using a nearest neighbor heuristic, persists routes and stop orderings in the
multi tenant schema, and renders static map previews with labeled pins for each stop. Drivers

74

can be assigned to routes after generation, and proof of delivery records can be reviewed with
photo thumbnails and confirmation codes visible in the portal.
Considerable attention was given to strengthening the security posture of the platform.
Row Level Security policies now guard all sensitive tables ensuring strict tenant isolation
based on company membership. Helper functions such as is company member simplify policy
expressions while an RPC function for resolving driver emails to member UUIDs supports
cross table operations without exposing internal identifiers. Role based distinctions between
admin, dispatcher, and driver permissions are enforced at the database layer so that drivers can
update only their own tasks and telemetry while dispatchers and admins retain full management
capabilities.
Supporting services were refined and integrated more deeply into the application. The
Mapbox service handles forward geocoding with fallback query strategies and provides static
map URLs for route visualization. The AI service communicates with the DeepSeek API using
configurable base URLs and model identifiers, enabling both summary generation and multi
turn chat within the driver interface. Error handling, loading states, and connectivity indicators
were added throughout the user interface to provide clear feedback during network operations
and offline scenarios.
By the close of this phase the system had matured from isolated components into a
cohesive end to end workflow spanning task ingestion, route optimization, driver execution, and
proof capture. The groundwork is now in place for final polish, user testing, and any remaining
integrations required before demonstration and submission.
